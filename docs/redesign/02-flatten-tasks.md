# 개편 2단계 — 곡 계층 제거(작업 평탄화) (설계 · 2026-10-13 구현)

> 2026-10-13 작성. 전체 방향·확정 결정은 메모리 `erp-redesign-2026-10`, 1단계는 `01-quick-create.md`.
> 개편 단계: 1 빠른 생성(배포 완료) → **2 곡 계층 제거** → 3 청구 대기함·자유 라인 청구서(단가표 제거) → 4 정리.

## 1. 목표

작업을 **프로젝트에 바로** 붙인다. 곡은 별도 개체가 아니라 작업의 **곡명 텍스트**가 된다.

```
지금:  프로젝트 ─ 곡(project_tracks) ─ 작업(track_tasks)
2단계: 프로젝트 ─ 작업(곡명 · 곡 아티스트는 작업의 칸)
```

- 믹스 하나 넣으려고 곡을 먼저 만들 필요가 없다. 1단계 `/new`는 이미 곡을 자동으로 만들고 있는데, 2단계에서 그 우회가 사라진다.
- 3단계 '청구 대기함'은 세션과 작업을 프로젝트 구분 없이 한 목록으로 모은다. 작업이 프로젝트 id를 직접 가져야 그 쿼리가 단순해진다.

## 2. 현재 곡 계층이 실제로 하는 일 (코드 조사 결과)

| 쓰임 | 위치 | 2단계 후 |
|---|---|---|
| 작업의 프로젝트 찾기(`tr.project_id`) | 프로젝트 집계·청구 후보·매출·외주·대시보드·'내 프로젝트' 등 약 40개 쿼리 | `t.project_id` 직접 |
| 곡 제목(`tr.title AS track_title`) | 청구 라인 설명 "곡명 - 종류", 매출 상세, 외주 정산, 대시보드 할 일 | `t.song_title` |
| 곡별 아티스트(`tr.artist`) | 컴필레이션 등 곡마다 아티스트가 다를 때. 매출·외주 표시 | `t.song_artist`(선택) |
| 콘텐츠 유형(`content_type` Music/Video_Post) | 저장만 되고 화면 어디에도 안 쓰임 | **버림** |
| 작업 없는 곡(빈 곡) | 세션에서 녹음한 곡을 적어 두는 용도(실측) | 프로젝트 메모에 보존(§5) |
| 곡 삭제 = 하위 작업 일괄 삭제 | 곡·콘텐츠 탭 | 작업 개별 삭제만 |
| 곡 일괄 추가(줄바꿈) | 곡·콘텐츠 탭 | **작업 일괄 추가**로 대체(§4) |

과거 청구서의 `invoice_items.track_title`은 발행 시점 스냅샷이라 **건드리지 않는다**(과거 청구서 표시 불변).

## 3. 데이터 변경

`track_tasks` 테이블을 재구성한다(SQLite는 `NOT NULL` 제거·컬럼 삭제를 ALTER로 못 해서 새 테이블로 복사 후 교체 — 기존 `session_directors_new` 등과 같은 방식).

| 컬럼 | 변경 |
|---|---|
| `project_id` | **추가** `NOT NULL REFERENCES projects(id) ON DELETE CASCADE` — 곡의 project_id로 채움 |
| `song_title` | **추가** TEXT(NULL 허용 = 표시는 프로젝트 이름) — 곡 제목으로 채움 |
| `song_artist` | **추가** TEXT(NULL = 프로젝트 아티스트) — 곡 아티스트로 채움 |
| `track_id` | **제거** |
| 나머지(종류·금액·엔지니어·외주 지급·청구 상태·작업일 등) | 그대로, **id 보존** |

- **id를 보존**하므로 `invoice_items.task_id`(청구 라인 → 작업) 연결이 그대로 유지된다. 재구성 중엔 외래키 검사를 끄고, 끝난 뒤 `foreign_key_check`로 확인한다.
- **테이블 이름은 `track_tasks` 그대로 둔다.** `tasks`로 바꾸면 쿼리·테스트 수십 곳을 함께 고쳐야 하는데 얻는 건 이름뿐이다. 이름 정리는 4단계에서 판단.
- `project_tracks`는 **이번 단계에선 지우지 않고 읽지만 않는다**(되돌릴 근거로 한 배포 주기 보존). 4단계에서 삭제.
- 마이그레이션은 기존 규약대로 `admin_state` 게이트(`tasks_flatten_v1`)로 1회만, 한 트랜잭션. 실행 전후 작업 수·청구된 작업 수·지급 완료 작업 수가 같은지 검사하고, 다르면 롤백하고 서버 기동을 멈춘다.

## 4. 화면 변경

### 프로젝트 상세 — '곡 · 콘텐츠' 탭 → '작업' 탭
```
작업                                          [+ 작업 추가]
┌ 타이틀곡 ─────────────────────── [이름 바꾸기] [+ 보컬튠][+ 믹싱][+ 마스터링][기타 ▾]
│  보컬 녹음 · 김OO · 10/2          ✓ 완료
│  믹싱 · 박OO                      − 완료
└──────────────────────────────────────────────
┌ 수록곡 2 ───────────────────────── …
└ (곡명 없음 = 프로젝트 이름으로 묶임)
```
- 같은 곡명끼리 **보기로만** 묶는다(개체가 아니라 그룹 머리글). 곡 순서 = 그 곡의 첫 작업이 등록된 순서.
- 그룹 머리글의 빠른 추가 버튼(보컬튠·믹싱·마스터링·기타)은 지금과 같다. 누르면 그 곡명으로 작업이 생긴다.
- **[이름 바꾸기]**: 그 프로젝트에서 같은 곡명을 가진 미청구 작업의 곡명을 한 번에 바꾼다. 청구된 작업은 잠금 규칙대로 그대로 두고 안내한다.
- **작업 폼**(행을 펼치면): 종류 · 곡명 · 작업일 · 담당 엔지니어 · 외주 지급단가 + ▸ 곡 아티스트(선택). 곡명을 바꾸면 다른 그룹으로 옮겨진다.
- **작업 추가 폼**: 종류 + 곡명(**여러 곡은 줄바꿈** → 곡마다 작업 하나) + 작업일 + 담당 엔지니어. 옛 '곡 일괄 추가'를 대신한다. 예: "믹싱 / 10곡"을 한 번에.
- 곡 삭제 버튼은 없어진다. 작업을 하나씩 지운다(청구·지급 잠금 규칙 동일).

### `/new` 작업
- 곡명 칸을 여러 줄 입력으로 바꾸고, 줄마다 작업을 하나씩 만든다.
- `resolveTrackForQuickTask` 우회는 삭제한다.

### 그 밖의 표시
- 청구 폼·청구 라인: `곡명(없으면 프로젝트 이름) - 종류` — 지금 형식 그대로.
- 매출·외주 정산·대시보드 할 일: `track_title` 자리에 `song_title`(없으면 프로젝트 이름).

## 5. 확정된 결정 (2026-10-13)

1. 곡별 아티스트 = **남긴다**(`song_artist`, 작업 폼의 접힌 칸, 비우면 프로젝트 아티스트).
2. 작업 없는 빈 곡 = **프로젝트 메모 끝에 `곡: A, B` 형태로 덧붙여 보존**한다(2026-10-13 수정 — 리허설 실측으로 빈 곡 32개가 '세션에서 녹음한 곡 기록'으로 쓰이고 있음을 확인. 버리면 30개 프로젝트의 녹음 곡 기록이 사라진다). 이미 메모에 같은 곡명이 있으면 다시 붙이지 않는다.
3. 운영 백업 리허설 = **한다**(최신 백업 1개, 스크래치 폴더에서만, 끝나면 삭제).

## 6. 진행 순서

1. ~~운영 백업 실측~~ 완료(§5-1). 구현 후 같은 백업으로 마이그레이션 리허설
2. 마이그레이션(`tasks_flatten_v1`) + 검사 + 테스트
3. 쿼리 전환(`JOIN project_tracks` 약 40곳 → `t.project_id`/`t.song_title`/`t.song_artist`)
4. 프로젝트 '작업' 탭 UI(그룹 보기·이름 바꾸기·일괄 추가)
5. `/new` 작업 여러 곡
6. 테스트 정리(곡을 만드는 기존 테스트 약 18개 파일) → 미리보기 확인 → 배포
   - 배포 직전 수동 백업 1회(cron 백업 엔드포인트) — 마이그레이션이 데이터 구조를 바꾸므로.

## 7. 범위 밖 (3·4단계)

- 믹싱·마스터링 **세션 종류**와 믹싱·마스터링 **작업**이 겹치는 문제(후반작업 세션의 '청구 미착수' 플래그, `track_tasks.session_id` 레거시) — 청구 개편(3단계)에서 함께 정리.
- 작업의 `billing_type`·`quantity`(사실상 고정값) 컬럼 정리, 테이블 이름 정리, `project_tracks` 삭제 — 4단계.
