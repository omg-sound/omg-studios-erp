# 청구 생성 폼 — 세금계산서 발행 이메일 필드(이번 청구서에만) 설계

- 날짜: 2026-07-27
- 상태: 설계 확정(사용자 승인) → 구현 계획으로
- 요청: "프로젝트 청구에서 청구처 선택하면 이메일 주소 필드 보여주고, 주소 임의로 추가할 수 있게"

## 배경

청구처의 세금계산서 발행 이메일(`parties.email`)은 청구 생성 폼에는 안 보이고, 발행 후 청구처 정보 카드에서만 보인다. 발행 시점에 "이 청구서는 다른 주소로 보내야 한다"는 경우(담당 회계가 건별로 다름 등) 청구처 정보를 고치지 않고는 방법이 없다.

**사용자 결정(2026-07-27)**: 입력한 이메일은 **이번 청구서에만 기록**한다(발행 스냅샷 `payer_snapshot.email`). 청구처(party) 정보는 바꾸지 않는다. (대안이었던 '청구처 정보에 저장'·'이메일 여러 개 목록'은 기각.)

## 동작 규칙 — WYSIWYG (사용자 확정)

청구처를 선택하면 그 청구처의 현재 이메일이 필드에 **미리 채워진다**. 제출 시 **필드에 보이는 값 = 이번 청구서의 발행 이메일**이다.

| 필드 상태 (제출 시) | 이번 청구서의 발행 이메일 | 스냅샷 처리 |
|---|---|---|
| 프리필 그대로 (청구처 이메일과 동일) | 청구처 기본 이메일 | 기존과 동일 (플래그 없음) |
| 다른 주소 입력 | 그 주소만 | `email` 덮어씀 + `email_overridden: true` |
| 빈칸으로 지움 | **이메일 없음** | `email: null` + `email_overridden: true` |

빈칸 = 폴백이 아니라 **"이 메일로는 보내지 않겠다"는 명시적 의사**로 취급한다(프리필이 있으므로 빈칸은 항상 의도적 행위 — 지운 값이 몰래 되살아나는 놀람 클래스 방지, 이 앱의 명시적 저장 철학과 일치).

**JS 미동작 안전망**: 이 규칙은 "프리필을 봤다"가 전제다. JS가 필드를 채울 때 hidden 마커 `payer_email_set=1`을 함께 세팅하고, 서버는 **마커가 있을 때만** 위 규칙을 적용한다. 마커 없으면(JS-off 제출) 기존대로 청구처 이메일이 스냅샷에 들어간다 — 빈 필드 제출이 이메일을 조용히 지우는 사고 방지.

## UI (프로젝트 청구 탭 · 청구 생성 폼)

- 위치: 청구처 콤보(`payerCombo`) + 추천 칩 아래, `data-payer-fix` 경고 블록과 별개의 행.
- 라벨: **"세금계산서 발행 이메일"**. 청구처 **선택 시 표시**, 미선택이면 숨김(기존 `data-payer-fix`와 같은 show/hide 패턴).
- 청구처 선택(콤보 pick·추천 칩·초안 복원 `__pkSet`) 시 그 청구처의 이메일로 프리필 + `payer_email_set=1`.
- 프리필 데이터: 콤보 옵션 JSON(`data-pk-options`)에 `email` 필드 추가 — 서버 왕복 없음.
  - `contactOptions()`는 이미 `email` 포함. `clientOptions()`(src/data/parties.js)에 `p.email` 컬럼 추가 필요.
  - 옵션에 없는 당사자(추천 칩의 관계자 등 id만 세팅되는 경로)는 프리필 불가 → 필드는 빈 값으로 표시하고 `payer_email_set`은 세팅하지 않는다(모르는 이메일을 지운 것으로 오인 방지 — 서버가 기존대로 party 이메일 스냅샷). 단 **사용자가 이 필드에 직접 입력하면**(input 이벤트) 그때 마커를 세운다 — 마커 규칙: **프리필했거나 사용자가 직접 편집했으면 1**.
- 청구처를 바꿔 선택하면 프리필도 그 청구처 값으로 교체(직접 입력했던 값은 버림 — 다른 청구처의 이메일이 남는 사고 방지).

## 데이터 흐름

1. 폼 제출: `payer_email`(텍스트) + `payer_email_set`(hidden, JS 세팅) → `POST /projects/:id/invoices/from-tasks`.
2. 서버(라우트 → `createInvoiceFromTasks`): `payer_email_set=1`이고 trim한 값이 청구처 현재 이메일과 다르면, `snapshotPayer()` 결과 JSON을 파싱해 `email`을 입력값(빈값이면 null)으로 교체하고 `email_overridden: true`를 추가해 저장.
3. 다운스트림은 무변경으로 자동 반영: 청구처 정보 카드(`payerInfoCard`)·발행 알림 메일·PDF 모두 스냅샷 우선(`payerView`)이라 임의 입력 주소가 그대로 보인다.

### 형식 검사

- 값이 있으면 간단 형식 검사(`이름@도메인.tld` 수준, 설정의 알림 메일 검증과 같은 강도). 불량이면 청구 생성 차단 + 기존 from-tasks 오류 경로(`PAYER_EMAIL_INVALID`)로 안내.

## 기존 로직과의 정합

- **`payerSnapshotChanged`**(src/data/invoices.js): 스냅샷에 `email_overridden`이 참이면 `email` 필드는 비교에서 **제외** — 임의 주소 ≠ party 이메일이라는 이유만으로 "⚠️ 청구처 정보가 업데이트되었습니다" 거짓 경고가 뜨지 않게.
- **`POST /invoices/:id/refresh-payer`**: 재스냅샷 후, 기존 스냅샷이 `email_overridden`이면 `email`·`email_overridden`을 **보존**해 저장 — [새로고침]이 임의 입력 주소를 party 이메일로 덮지 않게. 다른 필드(상호·주소 등)는 정상 갱신.
- 청구서 수정 없음 원칙 유지: 발행 후 이메일을 바꾸려면 기존대로 삭제 후 재발행.

## 임시저장(초안)

- `payer_email` 값을 초안(localStorage `invdraft:<projectId>`) 항목에 **포함**한다 — '발행 직전 결정' 필드 성격(청구처·할인·제목과 동급).
- 복원 순서 주의: `__pkSet`(청구처 복원)이 프리필로 필드를 덮으므로, **초안의 이메일은 그 뒤에** 복원한다(복원도 사용자 결정의 재현이므로 마커 세팅).

## 테스트

- 데이터: 스냅샷 override 3분기(동일=플래그 없음 / 다른 주소 / 빈값=null) + 마커 없으면 기존 동작 + `payerSnapshotChanged` 이메일 제외 + refresh-payer 보존. (기존 party/invoice 테스트 파일에 추가.)
- UI 계약(guardrails-ui data-* 마커) 및 jsdom 상호작용(ui-interactions): 청구처 선택 → 필드 표시·프리필·`payer_email_set` 세팅, 청구처 교체 시 프리필 갱신, 초안 저장·복원.

## 범위 밖

- 청구처 정보(`parties.email`) 수정 — 기존 청구처 편집 화면의 역할.
- 이메일 여러 개 목록 관리.
- 발행된 청구서의 이메일 수정(삭제 후 재발행 원칙 유지).
- 알림 메일 발송 로직 변경(스냅샷을 읽으므로 자동 반영, 코드 무변경).
