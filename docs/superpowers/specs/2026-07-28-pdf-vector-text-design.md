# 거래명세서 PDF 벡터 텍스트 전환(PDFKit) 설계

- 날짜: 2026-07-28
- 상태: 설계 확정(사용자 승인) → 구현 계획으로
- 요청: "견적서·내역서에서 일본어가 안 나온다" + "PDF에서 한국어·영어 폰트가 미묘하게 번지듯 안 깔끔하다"

## 배경 — 두 증상은 같은 뿌리

현재 파이프라인은 `SVG 문자열 → resvg(SVG→PNG 1240×1754, ~150dpi) → pdf-lib(PNG을 A4 페이지에 이미지로 삽입)`이다. 즉 **문서 전체가 한 장의 저해상도 비트맵**이고, 글자는 픽셀이다.

- **번짐**: 150dpi 래스터라 글자 가장자리가 뭉개지고 확대·인쇄할수록 심해진다. 텍스트 선택·검색·복사도 불가능하다.
- **일본어·한자 누락**: 번들 폰트(`NotoSansKR-Regular/Bold.ttf`)의 cmap을 직접 파싱한 결과 **히라가나·가타카나·한자 글리프가 아예 없다**(한글+라틴 서브셋). 렌더 테스트에서 `こんにちは カタカナ 漢字`가 통째로 사라지는 것을 재현했다. 일본어뿐 아니라 **한자 표기 전부**가 대상이다.

## 채택안 — PDFKit + CJK 폰트 (프로토타입으로 검증 완료)

`pdf-lib` + `@pdf-lib/fontkit`으로 벡터 텍스트를 먼저 시도했으나 **폰트 서브셋 기능이 깨져 있다**: variable TTF·static TTF(glyf)·static OTF(CFF) 세 형태 모두에서 글자가 누락되거나 깨진 PDF가 나왔다(sips·macOS Quick Look 두 렌더러에서 동일 재현). 서브셋을 끄면(`subset:false`) 정상이지만 폰트 전체가 임베드돼 PDF가 한글 문서 1.9MB·일본어 포함 5.2MB로 부푼다.

**PDFKit은 같은 폰트로 서브셋이 정상 동작한다** — 동일 내용 PDF가 **9KB**(현재 PNG 방식 148KB보다 작다)이고 한글·영문·가나·한자·₩가 모두 선명하게 렌더됐다. 그래서 "문서에 CJK가 있을 때만 큰 폰트" 같은 분기가 **불필요**하다(사용자가 앞서 고른 '문서별 자동 선택'은 이 발견으로 폐기).

### 의존성 변화

| | 패키지 | 비고 |
|---|---|---|
| 추가 | `pdfkit` | PDF 생성 전담 |
| 제거 | `@resvg/resvg-js` | **네이티브 모듈** — 배포 환경에 prebuilt가 없으면 로드 실패라 지연 로드·`PDF_RENDERER_UNAVAILABLE` 방어 코드까지 있었다. 제거로 배포 리스크가 줄어든다 |
| 제거 | `pdf-lib` | 소비처가 `src/invoice-pdf.js` 하나뿐(확인 완료) |
| 제거 | `@pdf-lib/fontkit` | 이번 조사 중 임시 설치분 |

순증 0(1 추가 / 3 제거). '의존성 0' 원칙의 예외로 사용자 승인을 받았다.

### 폰트

`public/fonts/NotoSansKR-Regular.ttf`·`NotoSansKR-Bold.ttf`를 **CJK를 커버하는 동명 파일로 교체**한다(파일명 유지 — 다른 코드가 이름에 의존하지 않지만 diff를 작게).

- 출처: `notofonts/noto-cjk` 의 `NotoSansKR-VF.ttf`(OFL) → `fonttools varLib.instancer`로 `wght=400`·`wght=700` static 인스턴스 생성.
- 커버 확인(직접 검사): 한글·히라가나·가타카나·CJK 한자·일본 고유한자(峠)·₩ 모두 포함.
- 파일 크기 약 5.9MB × 2. PDFKit이 서브셋하므로 **PDF 크기와 무관**하다(리포·배포 번들만 커진다).
- ⚠️ 폰트 생성은 **1회성 개발 작업**이다(fonttools는 Python 도구, 런타임 의존성 아님). 재생성 절차를 이 문서에 남긴다.

## 구현 전략 — 헬퍼만 교체, 레이아웃은 보존

`buildSvgPages()`(src/invoice-pdf.js)의 레이아웃 로직은 `text()`·`line()`·`rect()` 세 헬퍼로만 그린다. **PDFKit은 SVG와 좌표계가 같다**(원점 좌상단, y가 아래로 증가) — 그래서:

1. 페이지를 A4(595.28×841.89pt)로 만들고 `doc.scale(595.28/1240)`을 적용하면 **기존 1240×1754 좌표·폰트 크기를 그대로 쓸 수 있다**.
2. 세 헬퍼를 "SVG 문자열 반환" → "`doc`에 그리기"로 바꾼다. 레이아웃 계산 코드(페이지 분할·합계 블록·표 행)는 **문자열 누적(`svg += …`)만 함수 호출로** 바뀌고 좌표·크기·색은 그대로다.
3. 매핑:
   - `text(x,y,s,{size,weight,anchor,color})` → `doc.font(weight>=600 ? BOLD : REGULAR).fontSize(size).fillColor(color)` + `anchor==="end"`이면 `x - doc.widthOfString(s)`로 x 보정. ⚠️SVG `y`는 **베이스라인**, PDFKit `doc.text`의 y는 **텍스트 상단**이라 `y - ascender`로 보정한다(폰트 메트릭에서 산출).
   - `line(x1,y1,x2,y2,color,w)` → `doc.moveTo().lineTo().lineWidth(w).strokeColor(color).stroke()`
   - `rect(x,y,w,h,{fill,stroke,sw})` → `doc.rect(...)` + `fill`/`stroke`/`fillAndStroke`
   - 로고(`<image href="data:...">`) → base64를 Buffer로 디코드해 `doc.image(buf, x, y, {fit:[w,h], align:'right', valign:'top'})`
4. 페이지 전환: 현재 `pages` 배열 구조를 유지하되 각 페이지를 **그리기 콜백 배열**로 바꿔 `doc.addPage()` 후 실행한다.

이 방식이면 **레이아웃 수치가 하나도 안 바뀌므로** 회귀 위험이 레이아웃 전면 재작성보다 훨씬 작다.

### 하위 호환

- `renderInvoicePdf(data)`의 시그니처·반환(Buffer)은 **불변** — 라우트 3곳(청구 상세·프로젝트 청구 탭 미리보기·발행분)은 무변경.
- `buildSvg()`(첫 페이지 SVG 반환, 테스트·미리보기용)는 소비처를 확인해 **제거 또는 대체**한다.
- `PDF_RENDERER_UNAVAILABLE` 분기: resvg 제거로 원인이 사라지므로 **삭제**하고, 라우트 2곳(`projects.routes.js`·`invoices.routes.js`)의 대응 처리도 함께 정리한다.

## 검증

기계 검증만으로는 "글자가 실제로 보이는지"를 못 잡는다(현재 결함도 테스트를 다 통과하며 존재했다). 그래서 **렌더 검증을 필수 단계로** 둔다.

1. **단위/계약 테스트**: 페이지 분할(항목 11개 이하/초과), 합계 블록 3분기(할인 없음·할인 있음·VAT 0), 견적서 문구·번호 접두, 반환이 Buffer이고 `%PDF` 매직으로 시작.
2. **문자 렌더 회귀**(신규): 생성한 PDF에서 **텍스트를 추출**해 한글·일본어·한자·₩가 실제로 들어갔는지 확인한다(PDFKit 벡터 텍스트라 추출 가능 — pdf-lib 이미지 방식에선 불가능했던 검증). 추출 도구가 없으면 PDF 내부 스트림에서 폰트·ToUnicode 존재를 확인하는 수준으로 최소 잠금.
3. **육안 확인**(사람): 실제 청구서로 1페이지·다중 페이지·로고 포함·견적서 3종을 렌더해 배치가 기존과 같은지 확인한다. ⚠️크롬 PDF 뷰어는 스크린샷에 안 잡히므로(기록된 함정) macOS Quick Look(`qlmanage -t`)으로 이미지화해 비교한다.

## 범위 밖

- 거래명세서 레이아웃 자체의 디자인 변경(이번엔 **같은 배치 유지**가 목표).
- 중국어 간체 전용 글리프(현재 폰트는 한국어 기준 — 간체자 일부 미포함 가능).
- 세로쓰기·복잡한 텍스트 레이아웃.
