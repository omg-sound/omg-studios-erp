# 색상 체계 점검·개선 설계 (2026-07-30)

> 전날(2026-07-30) 팔레트 5종을 폐지하고 단일 테마로 접은 직후, **한 색 체계에 집중해** 전수 점검하고 고친다.
> 사용자 지시: "테마 하나만 남겼으니까 한 색상 집중해서 점검하고 개선해줘." 우선순위는 **읽힘 우선 + 시각 계층 정리 둘 다**(사용자 선택).

> ⚠️ **사후 정정(같은 날)**: 아래 «결정 1. 바닥 구조»의 **회색 캔버스(#F7F8F8)는 구현 후 사용자 판단으로 되돌렸다**('바탕은 흰색이 깔끔하다'). 회색 페이지가 `bg-bg`(페이지색)를 카드 안쪽 채움으로 쓰는 기존 관용구와 겹쳐 설정 화면이 얼룩덜룩해졌기 때문이다. **현재는 페이지·카드 모두 흰색**이고, 깊이는 보더 + `.row-link`의 전경색 hover 오버레이가 만든다(설정 화면 톤도 한 겹으로 정리). 나머지 결정(색을 배지 기준선까지 짙게 · 폼 경계 토큰 · 차트 토큰화 · 캘린더 점 · 대비 테스트)은 **모두 유효**하다.

## 왜 지금인가

팔레트가 5벌일 때는 어느 조합이 문제인지 특정하기 어려웠다(5팔레트 × 라이트/다크 × 4표면 = 40조합). 축이 하나로 줄어 **전수 계산이 가능해졌고**, 실제로 계산해 보니 문제가 라이트 모드에 몰려 있었다.

## 점검 결과 (토큰 조합 전수 계산)

측정 방법: `--color-*` 토큰에서 RGB를 읽어 WCAG 상대휘도 → 대비비를 계산. 배지는 `bg-*/12` 틴트를 표면 위에 알파 합성한 뒤 같은 색 글자와 비교(실제 렌더 구조와 동일).

| # | 발견 | 수치 | 범위 |
|---|---|---|---|
| 1 | 카드·표가 페이지와 같은 흰색 | `surface` vs `bg` = **1.00** | 깊이가 보더 1.31:1 + 옅은 그림자에만 의존. 행 hover 1.07 |
| 2 | 배지 6종 전부 AA 미달 | 3.26~4.27 | `badge-*` 45곳 |
| 3 | 상태·액센트 텍스트 미달 | primary 4.02 · warning 3.73 · danger 4.38 | 154곳 |
| 4 | `muted` on `elevated` 미달 | 4.24 | 11곳 |
| 5 | 버튼 채움 흰 글자 | 라이트 4.02 · 다크 3.65 | `btn-primary` 43곳 |
| 6 | 다크 경계 3건 | badge-primary 4.00 · badge-danger 4.15 · elevated 위 primary 3.94 | — |
| 7 | 매출 차트 색이 액센트와 다른 계열 | 순이익 #22c55e는 흰 배경 2.14 | 2줄 |
| 8 | 입력 경계(WCAG 1.4.11 3:1) | 1.41 | `.input` 1곳 |
| 9 | 캘린더 점이 상태를 **색으로만** 전달 | 파랑↔그린 명도차 1.11 | 1곳 |

**틴트 알파로는 배지를 못 살린다**: 12%→6%까지 낮춰도 3.4~4.05에 머문다(틴트가 색상을 품고 있어 같은 색 글자와의 거리가 줄지 않는다). 그래서 **글자색을 짙게 하는 것이 유일한 해법**이고, 그러면 페이지·카드·elevated는 자동으로 함께 통과한다 → 배지 대비를 **설계 기준선**으로 삼는다.

## 결정과 근거

### 1. 바닥 구조 = 회색 캔버스 + 흰 표면

| 토큰 | 현재 | 확정 |
|---|---|---|
| `bg` | #FFFFFF | **#F7F8F8** |
| `surface` | #FFFFFF | 유지 |
| `elevated` | #F7F7F7 | **#F0F1F2** |
| `border` | #E1E1E1 | **#D8D9DB** |

표면이 직접 깊이를 만들어 그림자·보더에 기대지 않고, hover(회색→흰색)가 실제로 보이며, 본문은 항상 순백 위에 얹혀 대비가 최대가 된다. 대가: 전신 흰 핀터레스트 톤에서 한 발 벗어난다(사용자 승인).

### 2. 텍스트·상태색 = 배지 기준선까지 한 단 짙게 (라이트)

| 역할 | 현재 → 확정 | 최저 대비(페이지·카드·elevated·배지 중) |
|---|---|---|
| `primary` | #007AFF → **#0066CC** | 3.44 → **4.68** |
| `danger` | #D64545 → **#C62828** | 3.73 → **4.64** |
| `warning` | #B07A08 → **#8F6200** | 3.26 → **4.56** |
| `success` | #14823C → **#0F7034** | 4.17 → **5.20** |
| `info` | #0074B3 → **#00648F** | 4.27 → **5.42** |
| `muted` | #767676 → **#6B6B6B** | 3.95 → **4.55** |
| `fg` | #111111 유지 | 14.58 |

파랑은 후보 6개를 재고 **#0066CC**를 골랐다(사용자 선택). 애플 웹 링크색 #0071E3은 카드 위 4.70으로 통과하지만 회색 페이지 4.41·배지 3.98이 남아 미달이고, iOS #007AFF는 세 자리 모두 미달이다. **토큰은 하나로 유지**한다 — 채움용/텍스트용을 나누면 60곳 `text-primary`·43곳 `btn-primary`마다 "어느 쪽인가" 판단이 붙는다.

### 3. 다크 = 2색 보정 + 버튼 글자 반전

`primary` #0A84FF → **#3D9BFF**(배지 4.00→4.88) · `danger` #EB5757 → **#F27272**(4.15→4.96). 나머지 4색은 통과라 손대지 않는다.

⚠️ **`primary-fg`가 다크에서 흰색 → #111111로 바뀐다.** 토큰을 하나로 유지하는 대가다: 링크 글자는 어두운 배경 위에서 **밝아야** 하고 버튼은 그 색을 배경으로 쓰므로, 밝은 파랑 채움 위에서 4.5를 넘는 글자는 어두운 쪽뿐이다(#111 → 6.59, 흰색 → 3.18). 다크 모드 주요 버튼이 '밝은 파랑 + 진한 글자'가 된다(스포티파이 그린 버튼과 같은 구조).

### 4. 입력 경계 = `--color-border-strong` 신설

WCAG 1.4.11은 폼 컨트롤 경계에 3:1을 요구한다. **라이트 #949596(3.00) · 다크 #6E6E6E(3.27)** 을 신설해 **`.input` 한 곳에만** 적용한다. 카드·구분선은 #D8D9DB를 유지한다 — 장식적 경계는 1.4.11 대상이 아니고, 전부 짙게 하면 화면이 선으로 뒤덮인다. Material Design의 입력 보더도 같은 지점(#949494)이다.

### 5. 매출 차트 = 변수화 + 모드별 값

2026-07-19에 차트 색을 고정한 근거는 "스포티(그린) 팔레트에서 매출↔순이익이 겹친다"였고, **팔레트가 폐지돼 그 근거가 사라졌다.** 게다가 순이익 #22c55e는 흰 배경 2.14로 막대가 배경에 묻힌다(비텍스트 권장 3:1 미달).

`--chart-revenue`/`--chart-profit`으로 변수화: 라이트 **#0066CC / #0F7034**(5.23 / 5.83), 다크 **#4DA3FF / #4CB782**(7.19 / 7.56). 파랑↔그린 구분은 유지되고 액센트와 계열이 맞는다. **팔레트 의존이 아니라 모드 의존**이라는 점이 옛 결정과 다르다.

### 6. 캘린더 점 = 모양으로도 구분

`calendarDotColor`가 예정=파랑·완료=그린·취소=회색을 반환하는데, 라이트에서 파랑↔그린 명도차가 1.11이라 흑백·색약에서 구분되지 않는다(취소는 제목 '(취소)' 접두 + 흐림이 보완). **완료를 속 빈 원**(테두리만)으로 바꿔 색이 유일한 전달 수단이 아니게 한다.
